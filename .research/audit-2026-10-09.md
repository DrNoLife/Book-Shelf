Read-only multi-agent audit (8 areas, each finding adversarially verified). Build: 0 warnings, 0 errors. Tests: 1256 passed, 0 failed.

33 confirmed findings, 0 contested, 2 refuted. None rated critical or high.

## 1. [medium] A book whose volume could not be parsed is silently written as volume 1, collapsing a whole series into one volume
`LnShelf/LnShelf.Api/Features/Import/Services/DesiredVolumeStateMerger.cs:26` · data-integrity · area: import

**Impact:** Volumes 2 to N of a series disappear from the shelf. Their read status, owned flag, ISBN and dates are folded into volume 1, which takes the strongest read status and the latest read date. The commit reports success, the user sees no error, and the shelf is wrong.

**Trigger:** Titles that fail to parse, such as 'Mushoku Tensei (Light Novel) Vol. 1' to 'Vol. 5'. Each becomes its own group with VolumeNumber null. The user resolves all five to the same AniList series, because it is the right series. CommitAsync merges them via ImportShelfWriter.ApplyAsync(Merge(groups)) and all five rows land on volume 1.

**Evidence:** `var volumeNumber = row.VolumeNumber ?? 1;` with the comment 'A book with no volume number in its title is the series in one volume, which is volume 1'. `merged[volumeNumber] = merged.TryGetValue(volumeNumber, out var existing) ? Combine(existing, incoming) : incoming;`. The assumption holds only for a true standalone. It is wrong for any volume the parser failed to read (see the BookTitleParser finding). Those titles produce a distinct SeriesKey each, so they become separate groups, and CommitAsync then regroups by MatchedAniListId.

**Suggested fix:** In Merge, do not default to 1 when other rows resolving to the same series already claim volume 1. At minimum, refuse the commit, or flag the group as NeedsReview, when more than one null-volume row maps to one AniList id. A cheaper option is to default to 1 only when the series group has exactly one row in total.

## 2. [medium] A volume's announced release date is never corrected when the store later moves it
`LnShelf/LnShelf.Api/Features/Metadata/Services/VolumeFactWriter.cs:125` · data-integrity · area: sync

**Impact:** When a publisher delays a book, the shelf keeps the old announced date. The Upcoming view and the 'out / to buy' captions show the wrong day, and after release the volume carries a date that never matched. This is the exact case the 'announced-becomes-dated upgrade' is meant to cover.

**Trigger:** Apple lists vol 14 as 2026-12-08, the first sync writes it (the volume is not released, so no conflict), and the publisher slips it to 2027-02-02. Every later night the catalogue pass sees 2027-02-02 != 2026-12-08, passes the conflict check, then returns at the line above. The volume keeps 2026-12-08 for good, and the placeholder-cover guard does not help once the real cover arrives.

**Evidence:** `if (volume.ReleaseDate is not null && !facts.MayReplaceReleaseDate) { return; }`. The Apple Books mapper hardcodes `MayReplaceReleaseDate = false` in VolumeFactsMapper.ToFacts, and nothing records which source wrote the existing date. So any date already on the volume blocks every later store date. Only Open Library can replace one, and only for volumes with a resolvable ISBN. VolumeGaps.NeedsAnything does not treat a still-future date as a gap.

**Suggested fix:** Let a store date replace the stored date when the stored date is still in the future (an announcement that has not matured), or when the same source wrote it. That means either a provenance column or a rule: `MayReplace || volume.ReleaseDate > today`. Add a test where the date moves from future A to future B and from future A to past B.

## 3. [medium] Publication status is read from any clause of the multi-line MangaUpdates status, while the count is read from the LN clause only
`LnShelf/LnShelf.Api/Features/Metadata/Mappers/MangaUpdatesSeriesMapper.cs:181` · bug · area: sync

**Impact:** An ongoing light novel can be flipped to Completed, and the flip never reverts. The user then sees the wrong publication status and the wrong 'ongoing' filters, with no discrepancy recorded.

**Trigger:** MangaUpdates status `"14 WN Volumes (Complete)\n23 LN Volumes (Ongoing)"` on a tracked light novel. The count is 23, but 'complete' is found in the WN clause, so PublicationStatus becomes Completed. A later `"... (Hiatus)"` in a Part clause has the same problem.

**Evidence:** `ToPublicationStatus` uses `Mentions(status, "cancel") / "hiatus" / "complete"` over the whole free-text status. MangaUpdatesVolumeCountParser deliberately picks one clause (LN over WN), and its tests show statuses such as `"14 WN Volumes + 2 SS Volumes (Complete)  \n23 LN Volumes + 2 SS Volumes (Complete)"` and `"168 WN Chapters + 3 Extra (Deleted)  \n8 LN Volumes (Complete)"`. SeriesRefresher.ApplyPublicationStatus (lines 264-281) writes Completed whenever IsCompleted is true and only records a discrepancy in the opposite direction.

**Suggested fix:** Parse status per clause and use the same clause the count came from (LN first, then the unqualified one). Add a parameterised test with the mixed WN-complete and LN-ongoing string.

## 4. [medium] Volume matcher accepts spin-off records whose qualifier is one word followed by a number
`LnShelf/LnShelf.Api/Features/Metadata/Services/VolumeEditionMatcher.cs:107` · bug · area: sync

**Impact:** A spin-off's date, cover, blurb and subtitle can be written onto the main series' volume N. The write happens unattended, and since the write is fill-if-null and covers are never replaced, it sticks.

**Trigger:** Series 'Sword Art Online' (light novel). The store or Open Library has 'Sword Art Online Progressive 3 (light novel)', so the remainder is `progressive 3 light novel` and the match returns number 3. ConfirmsMedium passes. If that record precedes the main vol 3 it supplies vol 3's date, cover and title. The same applies to 'Overlord Gaiden 2'.

**Evidence:** `TitleNormalizer.Tokenize(remainder).Take(LeadingTokenAllowance)` with LeadingTokenAllowance = 3, and the first integer token wins. The comment claims three tokens are 'not enough for a prefix collision', but a one-word qualifier plus a number fits easily. CatalogueVolumeMatcher uses `byVolumeNumber.ContainsKey` as first-wins, so the order of the store's response decides which record lands.

**Suggested fix:** Only accept a number that follows an explicit `vol`/`volume` token or comes directly after the series title (zero intervening alphabetic tokens). Reject remainders where an alphabetic token precedes the number unless that token is `vol` or `volume`. Add a Progressive/Gaiden regression test.

## 5. [medium] Cover upload is impossible in the volume list view (menu offers 'Set cover' but nothing happens)
`LnShelf/LnShelf.Client/Features/Series/Components/VolumeGrid.razor.cs:128` · bug · area: client

**Impact:** On a series shown as a list (per-series override or global List preference), the volume menu still shows 'Set cover…' / 'Replace cover…' and the footer 'Or drop an image straight onto the tile.' Clicking it silently does nothing, and there are no tiles to drop on. The user cannot set a cover override for any volume of a list-view series unless they switch to Tiles first.

**Trigger:** Open a series with the List view, click a row, choose 'Set cover…'. Nothing opens. Also true if the page was in Tiles, the user switched to List, then picked 'Set cover…' (stale/disposed tile reference).

**Evidence:** VolumeGrid.razor renders <VolumeList .../> without a CoverSelected callback when View == List. The only file input lives inside VolumeTile (InputFile in VolumeTile.razor:71). VolumePopover.razor:97-110 shows the cover rows regardless of view.

**Suggested fix:** Either hide the cover rows and drop hint in the popover when the view is List, or give the grid (not each tile) a single hidden InputFile that both views use for the picker. Show a message via SeriesState.ReportProblem if no picker is available.

## 6. [medium] 'Latest sync' query returns the newest started run, so unfinished runs and single-series refreshes hide the nightly review list
`LnShelf/LnShelf.Api/Features/Metadata/Services/SyncQueryService.cs:11` · bug · area: data

**Impact:** The sidebar footer and its 'N to review' discrepancies are replaced by an empty or irrelevant run. During a sweep, or after one that was interrupted, the sidebar shows a run with an empty Summary and no FinishedAt. Adding a series, or refreshing one on demand, creates a one-series SyncRun that becomes 'latest', so the previous nightly run's discrepancies (unmatched series, count conflicts, date conflicts) disappear from the UI.

**Trigger:** The nightly run records 5 discrepancies. The user then adds any new series. GET /api/sync/latest now returns the one-series run for the new series with 0 discrepancies, so the 5 items to review can no longer be seen.

**Evidence:** SyncQueryService orders `.OrderByDescending(candidate => candidate.StartedAt).FirstOrDefaultAsync(...)` with no filter on FinishedAt and no distinction between global and per-series runs. SeriesSyncService.StartRunAsync saves a new SyncRun on both RunAsync (line 20) and RunForSeriesAsync (line 70). AddSeriesPipeline.CompleteAsync calls RunForSeriesAsync after every add, and SyncRun.Summary is IsRequired but defaults to empty.

**Suggested fix:** Filter to FinishedAt != null. Store a scope flag (Global or Series) on SyncRun and have the sidebar query the latest finished Global run. Alternatively, do not persist single-series refreshes as SyncRuns, or attach their discrepancies to the existing latest global run.

## 7. [medium] Sync never creates volumes below the highest tracked number, so gaps left by an import stay missing for good
`LnShelf/LnShelf.Api/Features/Metadata/Services/SeriesRefresher.cs:223` · bug · area: data

**Impact:** For a series with only a few imported volumes, the missing lower volumes never appear. Examples are an LN where AniList has no volume count, or an export that lacks volume 1 or 4. 'To buy', the backlog counts, the next-to-buy volume and the bulk 'mark 1-N' action are then wrong or incomplete for that series. The 'N volumes tracked vs source says M' discrepancy is also miscounted.

**Trigger:** AniList returns no volume count, so the series is created with 0 volumes. The user imports a StoryGraph export containing volumes 2, 3 and 5. MangaUpdates says 10 volumes. Sync creates 6-10 (highestTracked is 5). Volumes 1 and 4 never exist, so the shelf shows them as neither owned nor to-buy.

**Evidence:** `var highestTracked = series.Volumes.Count == 0 ? 0 : series.Volumes.Max(volume => volume.Number); for (var number = highestTracked + 1; number <= sourceCount; number++)`. ApplyVolumeCount also gates creation on `sourceCount > trackedCount`, where trackedCount is series.Volumes.Count (a count, not a number range). ImportShelfWriter.ApplyVolume (added with IsLocalOnly = true) only creates the numbers present in the export.

**Suggested fix:** Create every number in 1..sourceCount that has no existing Volume, for example `Enumerable.Range(1, sourceCount).Except(series.Volumes.Select(v => v.Number))`. Compare the counts of distinct numbers when deciding whether volumes are missing.

## 8. [low] Nightly/global sync only persists at the very end; any abort or failed SaveChanges discards the whole sweep
`LnShelf/LnShelf.Api/Features/Metadata/Services/SeriesSyncService.cs:50` · data-integrity · area: data

**Impact:** A restart of the API container, a client/nginx timeout on POST /api/sync, or one failing DB write during an hour-long sweep throws away every volume count, release flag, ISBN enrichment, discrepancy and new-volume badge computed for all series. The run row stays unfinished. The covers were already cached in MinIO, so the lookup budget is spent again next time for nothing.

**Trigger:** Click 'sync now' (POST /api/sync, runs the full sweep inside the request) and let the request be cancelled by a proxy timeout or browser navigation. Or deploy or restart the container at 04:00 mid-sweep. Or delete a series in the UI while the sweep runs, so the final SaveChanges hits a DbUpdateConcurrencyException for that tracked-but-deleted row and fails for every series.

**Evidence:** The loop `foreach (var candidate in series) { await RefreshOneAsync(...); }` only mutates tracked entities. The only SaveChangesAsync calls in the class are in StartRunAsync (line 144) and FinishRunAsync (line 154), after the loop. RefreshOneAsync rethrows OperationCanceledException when the caller token is cancelled, and nothing catches a DbUpdateException from FinishRunAsync. All series (with Volumes and UserState) are loaded once into a single long-lived DbContext.

**Suggested fix:** Save after each series in RefreshOneAsync (and on failure detach or reload that series' entries), or give each series its own scope and DbContext. Always write FinishedAt and Summary in a finally block, with a non-cancelled token, so a partial run is still recorded.

## 9. [low] Auth model from spec section 7 is not enforced: whole app and /api reachable unauthenticated on port 8091
`docker-compose.production.yml:98` · security · area: infra

**Impact:** Anyone on the LAN (or anything that port-forwards or reverse-proxies 8091) can read and mutate the whole library, upload covers, trigger imports and syncs (which spend AniList/MangaUpdates rate budget). Spec section 7 promises proxy-level auth plus an internal header, and neither exists.

**Trigger:** `curl http://<server>:8091/api/library` from any LAN host returns data with no credentials; any POST/PUT/DELETE under /api works the same.

**Evidence:** compose: `ports: - "8091:80"`; nginx.conf has no auth_basic/auth_request and `location /api/` only sets Host/X-Forwarded-* headers; no `proxy_set_header X-LnShelf-Internal`. Program.cs has no middleware checking any header, and grep for `InternalHeader|X-LnShelf` across all *.cs returns nothing. compose comment line 101: `# Auth (§7) is not built yet — this stack is LAN-only until it is.` (acknowledged as not built, so this is a gap rather than an oversight).

**Suggested fix:** Minimum: add `auth_basic` + `auth_basic_user_file` (htpasswd mounted from the server override) to `server` in nginx.conf; add `proxy_set_header X-LnShelf-Internal $secret` in /api/ (secret from an env-templated conf via nginx `envsubst` templates) and a tiny middleware in Program.cs that returns 401 when the header does not match LnShelf__InternalHeaderSecret (skipped in Development). Note nginx does not strip a client-supplied X-LnShelf-Internal unless the proxy_set_header overrides it, which it will once set.

## 10. [low] Volume number is not recognised when the title carries a (light novel) tag, a decimal volume, or no comma before Vol.
`LnShelf/LnShelf.Api/Features/Import/Services/BookTitleParser.cs:82` · bug · area: import

**Impact:** The affected books come out as their own one-book series with no volume number, so the review queue fills with one NeedsReview card per book (NoCandidate or LowConfidence), or the books are mis-matched. A user with a Yen Press or Seven Seas export would have to resolve every volume by hand. The attached 76-row export does not contain these shapes, so every row there parses.

**Trigger:** Upload a StoryGraph export containing 'Overlord, Vol. 1 (light novel)', 'Series, Vol. 10.5' or 'Series (Light Novel) Vol. 3'. Parse falls through to `new ParsedBookTitle { SeriesTitle = title }`, so SeriesTitle becomes the whole raw string and VolumeNumber is null.

**Evidence:** CommaVolumePattern is ^(?<series>.+?),\s*Vol(?:ume|\.)?\s*(?<volume>\d{1,3})(?:\s*:\s*(?<subtitle>.+))?$. After the digits it accepts only ':' or end of string. StripTrailingBracket (line 70) removes only '[...]', never '(...)'. I ran the same regex in Python: 'Overlord, Vol. 1 (light novel)', 'Overlord, Vol. 3.5', 'Overlord, Vol. 3 - The X', 'Mushoku Tensei (Light Novel) Vol. 3', 'Sword Art Online 3: Fairy Dance' and 'Overlord, Vols. 1-2' all fail to match. The Open Library titles in docs/isbn-review.csv ('Overlord, Vol. 16 (light Novel)') show that publisher titles do carry the '(light novel)' suffix.

**Suggested fix:** Strip a trailing parenthesised format tag ('(light novel)', '(manga)', '(novel)') together with the bracket stripping. Then allow an optional decimal or range and any trailing text after the volume: Vol(?:ume|s?\.)?\s*(\d{1,3})(?:\.\d+)?\b with an optional subtitle after ':' or ' - '. Also accept 'Series Vol. N' without the comma. Add a regression test for each shape.

## 11. [low] Fallback (MangaUpdates) search is capped at 5 hits, unnarrowed, with no way to filter by format from the UI
`LnShelf/LnShelf.Api/Features/Metadata/Services/MangaUpdatesSearchCache.cs:62` · bug · area: search

**Impact:** While AniList is down, searching a franchise with many entries (e.g. a light novel plus several manga, spin-offs or adaptations) can return only 5 rows. The one the user wants, often the LN, may be missing. The page then shows an ordinary result list with no sign that it is truncated, and the user cannot narrow by format because the search page never sends format. The series looks unfindable.

**Trigger:** AniList returns 403 or an outage, so the fallback answers. Search a title that has a novel, several manga editions or adaptations and spin-offs (e.g. 'Re:Zero' or 'Overlord'). Only the first 5 hits by MangaUpdates ordering come back.

**Evidence:** MangaUpdatesSearchCache.FetchAsync: `Perpage = options.Value.SearchResultLimit` with `Type = [.. MangaUpdatesFormats.ToSourceTypes(format)]`. appsettings.json line 32 sets MangaUpdates `"SearchResultLimit": 5` (AniList uses 20). ## 12. [low] Shared lookup budget is spent in the same order every night, so permanent gaps starve later series
`LnShelf/LnShelf.Api/Features/Metadata/Services/IsbnVolumeEnricher.cs:73` · reliability · area: sync

**Impact:** Series late in the alphabet may never get covers, dates or subtitles. A few unresolvable volumes in early series use up the 60-lookup allowance every night, and the sync summary still reports a healthy run.

**Trigger:** Shelf with about 6 volumes that are permanent 404s with no verifiable candidate (the docs say about 20% of ISBNs are genuine gaps) in series sorting early. Those volumes consume all 60 units each night before the loop reaches later series.

**Evidence:** SeriesSyncService.RunAsync orders series by TitleEnglish and spends one `LookupBudget(MaximumLookupsPerRun = 60)` across all of them. `ApplyByIsbnAsync` does `budget.Spend(1)` per ISBN lookup, plus 1 for the search and 1 per verified candidate (up to CandidateIsbnLimit = 8) in ResolveBySearchAsync, about 10 per gap. VolumeGaps.WorthAskingByIsbn deliberately re-asks every gap each night. The charge applies even when HybridCache answers, because Spend happens before the cached call. CatalogueTitleArbiter.cs:56 charges 1 per title tried, up to 9 for a series the store does not carry. Nothing rotates the order or records a last-attempted time.

**Suggested fix:** Make the order fair: rotate the start series, or order by LastSyncedAt or a per-volume last-attempted timestamp so gaps back off. Alternatively cap the spend per series, give the catalogue its own budget, and do not charge the budget for cache hits.

## 13. [low] One SaveChanges at the end of the sweep: a failure there loses every series' refresh and leaves the run unfinished
`LnShelf/LnShelf.Api/Features/Metadata/Services/SeriesSyncService.cs:154` · reliability · area: sync

**Impact:** The per-series isolation only covers in-memory work. A database error at the final save (unique index violation, over-length string, concurrent run) discards the nightly results for the whole shelf and repeats the next night. The sidebar then shows a run with an empty summary and no FinishedAt. A container restart or cancel in the middle of a long sweep (OL at 12 requests a minute) loses all progress, and covers already pushed to MinIO are orphaned.

**Trigger:** Press 'Sync now' (POST /api/sync) while the 04:00 sweep is running, or while a series add is refreshing. Both load the same series and both try to create volume N+1 or link the same MangaUpdatesId. The second final save throws DbUpdateException and nothing from that run is persisted.

**Evidence:** RefreshOneAsync (lines 100-129) catches exceptions only around `refresher.RefreshAsync`. There is no SaveChanges in the loop (lines 50-53); the first save after StartRunAsync is `await dbContext.SaveChangesAsync(cancellationToken)` in FinishRunAsync, which is outside any try. Bounded columns include Volume.Title and SyncDiscrepancy.Note (1000) and Value (400), both fed from external text such as RawStatus and titles. The unique indexes on (SeriesId, Number) and MangaUpdatesId are also exposed.

**Suggested fix:** Save per series inside RefreshOneAsync's try, and on failure detach or reload that series' tracked entities and count a failure. Also serialise runs with a simple in-process lock or `SemaphoreSlim`, and truncate external text before it goes into bounded columns.

## 21. [low] Per-attempt timeout covers only the response headers; a stalled body hangs the whole sweep
